# Spec: Arrow-transport benchmark profile (memory + latency impact, RBAC on)

Status: ALL_OK

- **Slug / branch:** `feat/bench-arrow-transport`
- **Owner phase:** orchestrator → developer → reviewer; then orchestrator RUNS the benchmark and commits results.
- **Why:** #54 (zero-copy lazy-view sandbox) + #55 (Arrow IPC streaming transport) landed to cut the `/sql` API's high memory + latency. We need a reproducible benchmark that **quantifies the impact** — memory (peak RSS) and latency — of the Arrow transport vs JSON, **with RBAC enabled**, and **attaches** (does not replace) the existing JSON `-api` results.

## 1. Task
Add a new `api-arrow` benchmark profile (`make bench-api-arrow`, flag `--api --arrow`) that, with RBAC on, ingests via JWT and then measures, over the HTTP `/sql` API:
- **count** and **aggregation** via the **Arrow** transport (mirrors the existing api profile workloads, comparable to committed `-api`);
- a **large-result scan** run over **both JSON and Arrow** as two distinct monitored phases, to expose the transport's memory/latency delta.
Write NEW artifacts (`bench/results-api-arrow.*`, `bench/RESULTS-api-arrow.md`, `bench/charts-api-arrow/`) and append a new dated README subsection. Do NOT touch the committed `-api` files.

## 2. Design (resolved)

### Driver (`bench/internal/store`)
- Reuse the merged Arrow client methods (`CountMetricsArrowAPI`, `AggregateMetricsArrowAPI`, `ScanMetricsArrowAPI`).
- Add a JSON scan method `ScanMetricsJSONAPI(ctx, sqlText) (int64, error)` via the existing `postSQL` (JSON) path (returns row count) so the scan is measured identically over both transports.
- Scan SQL (both transports, identical): `SELECT "__name__", labels, value, ts FROM metrics LIMIT <N>` with `N = min(cfg.MetricsRows, SQL_API_MAX_ROWS)` (aim ~100k rows so the result set is large enough that JSON buffering vs Arrow streaming diverges). Both transports must return the same row count (correctness gate).

### Monitor phases (`bench/internal/monitor/series.go`)
- Add `PhaseScanJSON = "scan_json"` and `PhaseScanArrow = "scan_arrow"`.
- Reuse `PhaseCount`/`PhaseAggregation` for the Arrow count/agg (this profile drives them via Arrow).

### Orchestrator (`bench/cmd/prism-bench/main.go`)
- Add `--arrow` flag; require `--api` (error if `--arrow` without `--api`). When both set, `profile = "api-arrow"`.
- New runner (or extend `runAPIQueryPhase`) for the api-arrow path: logs_like (unchanged, engine-level) → `count` (Arrow) → `aggregation` (Arrow) → `scan_json` → `scan_arrow`. Keep the store stop/restart + count gate (store vs ClickHouse + exact `MetricsRows`).
- Emit workloads: `count`/`aggregation` (prism-store Arrow vs ClickHouse), and `scan` rows for `prism-store (JSON)` and `prism-store (Arrow)` (ClickHouse scan optional/omitted — the scan is a store transport comparison, document it as such).
- Extend the `usageFor`/`attachUsage` phase switch to attach the store series for `scan_json` and `scan_arrow` (per-phase peak RSS/CPU/IO), so the report captures memory per transport.
- Output paths via `results.ArtifactPaths(repoRoot, "api-arrow")`; charts via the api-arrow charts dir. Resource sampling uses the dynamic-PID store sampler (already in place for the api profile) so RSS is captured across the store restart.

### Rendering (`bench/internal/results`)
- Extend `render.go` for `profile == "api-arrow"`: title "Arrow transport profile (RBAC on)", workload table (count/aggregation Arrow vs ClickHouse; scan JSON vs Arrow), a per-phase resource table (peak RSS/CPU) highlighting `scan_json` vs `scan_arrow`, chart embeds from `charts-api-arrow/`, and caveats (JWT/RBAC overhead per request; scan is a store JSON-vs-Arrow transport comparison, not vs ClickHouse; Docker Desktop blkio-zero caveat retained).
- Reuse existing chart writers for the new profile's charts dir.

### Makefile / docs
- `Makefile`: `bench-api-arrow` target — `CGO_ENABLED=1 go run -tags duckdb_arrow ./bench/cmd/prism-bench --api --arrow --scale $(BENCH_SCALE)` (mirror `bench-api` caps/flags).
- `bench/README.md`: new section documenting the `api-arrow` profile, what it isolates (transport memory/latency with RBAC), and reproduce steps.
- Root `README.md`: append a NEW dated subsection under the benchmark area — "Arrow transport profile" — presenting the Arrow count/agg + the JSON-vs-Arrow scan (latency + peak RSS), and contrasting with the prior JSON `-api` section (~280–300 ms, ~471–483 MiB) to show the combined lazy-view (#54) + transport (#55) impact. **Keep the existing `-api` subsection intact.**

### Numbers are produced by the orchestrator run
- The developer lands the code + unit tests (render/paths/driver) and a compile/smoke check. The committed result files (`RESULTS-api-arrow.md`, charts, README numbers) are generated by the orchestrator's real `make bench-api-arrow` run (Docker + ClickHouse) in a follow-up step and committed then.

### Out of scope
- Changing the JSON `-api` profile or its committed results. Changing store/query code. Flight SQL. ClickHouse scan tuning (scan is a store transport comparison).

## 4. Decision log (Decision Protocol)
- **Isolate transport impact via a same-build JSON-vs-Arrow scan + Arrow count/agg, RBAC on, as a new attached profile.**
  - ref: Arrow IPC streaming format (https://arrow.apache.org/docs/format/Columnar.html#ipc-streaming-format); benchmarking guidance on measuring peak RSS per phase rather than allocated caps (existing `bench/README.md` methodology).
  - perf/memory: a large result set is where streaming (Arrow) vs full-buffer (JSON) memory diverges — measuring both on the same build isolates the transport from the lazy-view change. product: attaching (not replacing) preserves the historical record the user asked to keep; `make bench-api-arrow` keeps it reproducible by anyone with Docker.
